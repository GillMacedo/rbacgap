# Architecture

    parse flags --> go list -e -export -compiled -deps -json PATTERNS (any failure: exit 2)
      --> go list -e -f {{.ImportPath}} PATTERNS: every matched package must be in the first list
      --> type-check each main-module package from source, importing deps from export data
            (a package error, dependency error or type error: exit 2)
      --> read +kubebuilder:rbac markers: live ones become grants, attached ones are inert
            (a malformed live marker: exit 2)
      --> read --role files (unreadable: exit 2), CRD YAML for plurals (cut off: exit 2)
      --> walk each non-generated file: calls --> needs (group, resource, verb, call site)
            unknown kind --> UNCHECKED
      --> compare needs with grants --> MISSING, PARTIAL, MAYBE, UNUSED
      --> text or JSON --> exit code

- **The go command decides what is built.** Packages, files and dependencies come from `go list`, with the user's environment and `GOFLAGS` passed through. Packages of the main module that the patterns import are checked too, so `./cmd/manager` covers exactly that binary.
- **Types come from `go/types`.** Each target package is parsed and type-checked from source. Imports are read from the export data `go list -export` produced, through `go/importer`, so the tool needs no dependency of its own. Calls are recognized by the package path and receiver type name of the method `go/types` resolves, so embedded clients (`r.Get`), fields (`r.Client.Get`), wrappers and aliases (`ctrl.CreateOrUpdate`) all resolve the same way.
- **Kinds come from the static type of the object argument.** A list type's kind comes from its `Items` field. Interfaces, type parameters, `Unstructured` and `PartialObjectMetadata` can't be resolved statically and become UNCHECKED.
- **Groups and plurals.** The group comes from the defining package's `+groupName` comment, or a `GroupVersion` or `SchemeGroupVersion` literal, including one that uses a package constant. The plural comes from `+kubebuilder:resource:path` on the type, then CRD YAML anywhere in the module, then English rules. Built-in kinds use the rules Kubernetes uses for its own resources.
- **Cache.** controller-runtime's manager client serves Get and List from an informer, which lists and watches. A Get or List through it adds list and watch. Reads through `GetAPIReader()`, or a field or variable whose name says it's the API reader or uncached, don't.
- **Markers follow controller-gen.** controller-gen v0.17 to v0.23 only read `+kubebuilder:rbac` markers in comments that stand alone, or the package doc comment. A marker in a declaration's doc comment, or inside a declaration, is ignored. The tool reports those as inert and doesn't count them.
- **Matching follows the API server.** Verbs and resources are compared exactly, `*` matches anything, `*/sub` matches a subresource of any resource, and resourceNames rules don't allow list, watch, create or deletecollection. Namespace-scoped grants are PARTIAL, because the tool can't know which namespace a call uses.
- **Generated client code is skipped.** Files generated by `client-gen`, `informer-gen`, `lister-gen` or `applyconfiguration-gen` call the API on behalf of their callers, and the callers are checked instead. Other generated files, including cgo output, are checked.
- **Scope.** Built-in cluster-scoped resources, CRDs with `scope: Cluster` and types with `+kubebuilder:resource:scope=Cluster` can't be granted by a Role or a `namespace=` marker.

Key choices are in `decisions/`.
